## Reusable Production Smoke, Browser, Notification, Webhook, And Archive Acceptance Entry

The repository now includes `scripts/production-smoke.cjs`, exposed as `npm run smoke:production` and wired into the installed management CLI as `ou-ui smoke` / `ou sm`, for live HTTP deployment evidence collection. It also includes `scripts/production-browser-smoke.cjs`, exposed as `npm run smoke:browser` and wired into the installed management CLI as `ou-ui browser-smoke` / `ou bs`, for real browser workflow evidence collection. The browser smoke uses Playwright to drive the installed panel URL through login, key page navigation, screenshot capture, and logout without printing passwords, cookies, CSRF tokens, or bearer tokens. `scripts/production-notification-smoke.cjs`, exposed as `npm run smoke:notifications` and `ou-ui notification-smoke` / `ou ns`, logs in through the installed panel, reads Telegram settings, calls the protected Telegram test-notification API, and writes a sanitized report without printing passwords, cookies, CSRF tokens, bot tokens, chat IDs, or binding IDs. `scripts/production-webhook-smoke.cjs`, exposed as `npm run smoke:webhooks` and `ou-ui webhook-smoke` / `ou ws`, reads installed system-alert webhook configuration or explicit URLs, posts a sanitized test JSON payload, blocks localhost/private targets by default, and writes reports without bearer tokens, full URL paths, or query strings. `scripts/production-archive-smoke.ts`, exposed as `npm run smoke:archive` and `ou-ui archive-smoke` / `ou as`, reads installed external archive sink configuration and writes sanitized test audit anchors, Agent log archive summaries, and traffic compaction buckets to the configured local JSONL, webhook, and S3-compatible object-storage sinks; S3-compatible writes can include optional Object Lock retention/legal-hold headers in the SigV4-signed request, and the redacted report records only sanitized Object Lock policy summaries without webhook tokens, object-storage credentials, full URL paths, or query strings.

The installed CLI also exposes `ou-ui acceptance` / `ou qa`, which writes a timestamped evidence bundle under `/var/lib/ou-ui-next/acceptance/` containing doctor output, HTTP smoke terminal output, browser smoke terminal output, notification/webhook/archive-smoke skipped or executed evidence, optional external provider receipt/provider-evidence/timestamp-evidence attachments, optional clean-server install evidence attachments, optional Agent host evidence attachments, sanitized JSON reports, a `browser-screenshots.tar.gz` archive, and a manifest with per-file byte sizes and SHA-256 hashes for later archive verification. It now also exposes root-only `ou-ui archive-provider-evidence` / `ou ape`, which generates a sanitized `ou-ui-next.archive-provider-evidence.v1` summary from a passed archive smoke report plus explicit provider delivery, bucket Object Lock, and retention-policy confirmations; root-only `ou-ui timestamp-evidence` / `ou te`, which generates a sanitized `ou-ui-next.timestamp-evidence.v1` summary from a real artifact plus a real third-party timestamp receipt after explicit third-party/sanitized/verified confirmations while recording only basename/size/SHA-256 metadata; and root-only `ou-ui clean-install-evidence` / `ou cie`, which generates a sanitized `ou-ui-next.clean-install-evidence.v1` summary only after explicit clean-server and fresh-install operator confirmation, records optional redacted-transcript basename/size/SHA-256 without copying transcript text, and checks service/CLI/panel availability or explicit external-confirmation flags before writing evidence.

`ou d` / the bundle `doctor.txt` reports browser-smoke readiness too: presence of `scripts/production-browser-smoke.cjs`, Playwright module availability, and whether the Chromium executable exists. The same CLI exposes `ou-ui acceptance-verify` / `ou qv` to re-check bundle hashes after archiving or transferring the bundle; the verifier remains backward-compatible with older bundles that only contain the original doctor/smoke/report files or pre-webhook browser/notification evidence. For archived field evidence, `ou qv` can add strict report-content gates with `--require-runtime-evidence`, `--require-browser-smoke`, `--require-notification-smoke`, and `--require-webhook-smoke`, failing archived bundles whose runtime summary is incomplete, browser smoke was skipped/failed, browser screenshots were disabled/missing, Telegram notification smoke was skipped/failed, or webhook smoke was skipped/failed/missing sanitized target URLs. Bundles created with `ou qa --include-archive-smoke` can additionally use `ou qv --require-archive-smoke`, which fails if archive smoke was skipped/failed or the report is missing sanitized sink evidence.

Bundles that attach generic operator-sanitized provider receipts with `ou qa --external-receipt <path>` can use `ou qv --require-external-receipts`, which fails unless `external-receipts-manifest.json` records at least one receipt attachment and every copied receipt file still matches its recorded bundle path plus size/SHA-256. If one attached receipt uses sanitized `ou-ui-next.archive-provider-evidence.v1`, `ou qv --require-archive-provider-evidence` also enforces object-storage delivery plus provider-side Object Lock/retention proof fields without accepting obvious secret keys or tokens. If one attached receipt uses sanitized `ou-ui-next.timestamp-evidence.v1`, `ou qv --require-timestamp-evidence` enforces third-party timestamp receipt metadata, explicit confirmations, safe labels, and valid artifact/receipt path/hash fields without accepting obvious sensitive field names or query/credential-bearing URLs. The dedicated `ou qa --archive-provider-evidence <path>` and `ou qa --timestamp-evidence <path>` paths store both summaries in the same external receipt manifest and cause `ou qf` to enable external-receipt plus matching provider/timestamp strict gates automatically, without replacing real provider-console/API or TSA/OpenTimestamps proof.

Bundles that attach operator-sanitized clean-server install evidence with `ou qa --install-evidence <path>` can use `ou qv --require-clean-install-evidence`, which fails unless `install-evidence-manifest.json` records at least one attachment with a matching bundle path/hash and at least one copied JSON summary matches `ou-ui-next.clean-install-evidence.v1` with fresh-install, clean-server, installer-exit, service-active, CLI-installed, and panel-reachable evidence while rejecting obvious secret field names and URL credentials/query fragments. Bundles that attach `ou-agent qa` or `ou-agent qf` output with `ou qa --agent-evidence <bundle>` can use `ou qv --require-agent-evidence`, which fails unless `agent-evidence-manifest.json` records at least one Agent evidence bundle, copied Agent manifest/runtime/final-summary files match their hashes, the copied Agent manifest records a non-empty `bundleDirectory` plus `serviceStatus=0` and `runtimeSummaryStatus=0`, and the archived `runtime-summary.json` proves running Xray inbounds, running port-forwarding services, an empty pending queue, and healthy guardrail evidence.

Bundles produced by `ou qf` can also be rechecked with `ou qv --require-final-summary`, which verifies the base manifest has a non-empty `bundleDirectory`, `final-acceptance-summary.json` schema/status, a valid UTC `createdAt`, a non-empty summary bundle directory matching `manifest.bundleDirectory`, strict gate markers, and the recorded manifest/transcript path/size/SHA-256 against the archived files; `ou qvf` is the one-command wrapper that applies runtime, browser, notification, webhook, and final-summary strict gates together. When the final summary records optional archive/receipt/provider/timestamp/clean-install/Agent/Agent-final-summary gates as true, `ou qvf` now promotes those records into the current verifier requirements and rechecks the corresponding archived content instead of trusting only the final transcript marker. `ou qvr` is the stricter production release verifier: it requires runtime, browser, notification, webhook, archive smoke, external receipt, provider evidence, timestamp evidence, clean-install evidence, Agent evidence, Agent final-summary evidence, and final-summary gates at once, and fails if final summary does not record the optional gates, including `agentFinalSummary`, as true; if an archived bundle already has `release-acceptance-summary.json`, `qvr` also revalidates the release summary UTC `createdAt` and bundle directory against `manifest.bundleDirectory` or the current bundle directory, rechecks the release verifier transcript path/hash, promotes every release-summary gate back into current content checks, and manual `qvr --write-summary` can persist or overwrite the current release verifier transcript plus machine summary for both passed and failed manual runs. Failed manual summaries keep `status=failed`, the current `bundleDirectory`, and the current transcript path/hash, and refreshes skip stale release-summary self-validation before writing the new evidence. `ou-ui final-acceptance` / `ou qf` wraps the final field sequence into one command: it generates the bundle with runtime, Telegram, and webhook evidence collection enabled, leaves archive smoke skipped unless `--include-archive-smoke` is explicitly passed, can carry explicit `--external-receipt`, `--archive-provider-evidence`, `--timestamp-evidence`, `--install-evidence`, and `--agent-evidence` attachments, rejects `--skip-browser-smoke`, requires an explicit Telegram target, immediately runs the same strict `ou qv` gates against the bundle it just wrote, and automatically adds `--require-archive-smoke` / `--require-external-receipts` / `--require-archive-provider-evidence` / `--require-timestamp-evidence` / `--require-clean-install-evidence` / `--require-agent-evidence` to that verifier run when those external, provider-evidence, timestamp-evidence, clean-install, or Agent evidence inputs were explicitly requested. During `ou qfa`, the same final acceptance run also adds `--require-agent-final-summary`, so the Master `final-acceptance-verify.txt` and `final-acceptance-summary.json` record `agentFinalSummary=true`. It then saves the strict verifier transcript as `final-acceptance-verify.txt` and writes `final-acceptance-summary.json` with the manifest, verifier transcript path/size/SHA-256, and optional archive/receipt/provider-evidence/timestamp-evidence/clean-install/Agent/Agent-final-summary strict-gate flags for later `ou qvf` revalidation; the subsequent `qvr` transcript and machine summary are saved as `release-acceptance-verify.txt` and `release-acceptance-summary.json` even when that release verifier fails, and `ou qv --require-release-summary` can recheck that release summary after archive transfer.

To keep the bundle self-consistent, `ou qa` fixes the installed panel URL, root-only credentials file, backend env file, bundle-local report paths, screenshot directory, notification report path, webhook report path, archive report path, receipt manifest path, install evidence manifest path, and Agent evidence manifest path, while still allowing read-only smoke tuning flags such as `--timeout-ms`, `--insecure-tls`, `--skip-csrf-probe`, and `--require-runtime-evidence`; low-resource hosts can explicitly use `--skip-browser-smoke`, which records the skip in the manifest rather than pretending browser acceptance ran. Notification smoke and webhook smoke are skipped by default to avoid external side effects during every acceptance run; operators can opt in with `--include-notification-smoke --telegram-admin-chat-id <id>` or `--include-notification-smoke --telegram-binding-id <id>` for Telegram, and `--include-webhook-smoke` plus optional `--webhook-url` / `--webhook-urls` / `--webhook-bearer-token` / `--webhook-bearer-token-file` for real webhook delivery. Archive smoke is also skipped by default; operators can opt in with `--include-archive-smoke`, attach generic sanitized provider receipts with `--external-receipt`, attach provider immutable-retention summaries with `--archive-provider-evidence`, attach third-party timestamp summaries with `--timestamp-evidence`, attach sanitized clean-server install evidence with `--install-evidence`, attach Agent host evidence with `--agent-evidence`, and have `ou qf` or explicit `ou qv --require-archive-smoke --require-external-receipts --require-archive-provider-evidence --require-timestamp-evidence --require-clean-install-evidence --require-agent-evidence`, with `ou qvr` as the final all-gates shortcut, enforce those external, timestamp, clean-install, and Agent evidence gates for real field acceptance.

For production release evidence, `ou qv --require-agent-final-summary` now adds a stricter Agent host gate on top of `--require-agent-evidence`: the attached Agent bundle must include `ou-agent qf` output, the copied Agent manifest must still have a non-empty `bundleDirectory`, `serviceStatus=0`, and `runtimeSummaryStatus=0`, the Agent final summary must record a valid UTC `createdAt`, a non-empty `bundleDirectory` matching the copied Agent manifest bundle directory, and `runtimeEvidence=true`, its manifest/transcript paths and SHA-256 values must still match the copied files, and the transcript must retain the Agent runtime evidence pass marker. `ou qvr` and `ou qfa` enable this gate automatically so release verification cannot pass with only an `ou-agent qa` runtime bundle, and `ou qvr` also requires the Master final summary to record `strictGates.agentFinalSummary=true`.

`ou qfa` is now documented and tested as the production release acceptance orchestrator. It refuses to start unless `--include-archive-smoke`, `--archive-provider-evidence`, `--timestamp-evidence`, `--install-evidence`, and `--agent-evidence` are explicit, preflights provider/timestamp/clean-install/Agent evidence paths and content before smoke work starts, requires the Agent evidence to include `ou-agent qf` final host acceptance summary/transcript evidence, then runs strict `qf` with the Agent final-summary gate recorded in the Master transcript/summary and immediately runs `qvr` against the same bundle. The release verifier transcript is saved as `release-acceptance-verify.txt`, and `release-acceptance-summary.json` records pass/fail status plus bundle directory and paths/hashes for the manifest, final summary, and release transcript; manual `ou qvr --write-summary` writes the same files for an existing final acceptance bundle and is contract-tested for successful runs, failed runs, bundle-directory persistence, and stale release-evidence overwrite. The release-summary strict gate checks the release summary schema/status, valid UTC `createdAt`, non-empty bundle directory matching `manifest.bundleDirectory` or the current bundle directory, manifest/final-summary/release-transcript paths/hashes, every required release gate marker, and promotes those markers back into actual runtime/browser/notification/webhook/archive/provider/timestamp/clean-install/Agent/final-summary content checks; `qvr` applies that gate automatically when the archived bundle already contains a release summary. The content preflight builds a minimal temporary evidence bundle and calls the existing `ou qv` provider, timestamp, clean-install, Agent runtime, and Agent final-summary strict gates, so the early failure path shares the archived-bundle verifier semantics. This reduces operator error, but it does not create or replace real provider-console/API, third-party timestamp, clean-server install, or Agent-host evidence.

The HTTP smoke report records a sanitized runtime acceptance summary with counts for Agents, Agent sessions, Xray inbounds, port-forwarding rules/ports, quota states, task states, traffic rollups, system-alert severities/kinds, command dead letters, and audit health. It intentionally does not include Agent IDs, session IDs, forwarding IDs, tokens, cookies, CSRF values, or passwords. When `ou sm --require-runtime-evidence` or `ou qa --require-runtime-evidence` is used, the run fails unless the deployed Master shows at least one online/degraded Agent session, at least one Xray inbound, at least one port-forwarding rule/port, no critical system alerts, and no command dead letters; the failure reasons are preserved in `smoke-report.json`.

On each enrolled host, `ou-agent qa` now adds `runtime-summary.json` to the Agent evidence bundle. The summary records runtime file presence/size/SHA-256, module runtime states, Xray inbound counts, port-forwarding service counts, guardrail counts, and pending-event counts, while intentionally omitting raw artifacts, client UUIDs/emails, forwarding target addresses, and Agent tokens. `ou-agent qv` verifies this new file when present and remains compatible with earlier Agent bundles that only contain doctor, service status, and redacted log-tail evidence. For final host-side runtime acceptance, `ou-agent qv --require-runtime-evidence` now fails archived bundles unless the base Agent manifest has a non-empty `bundleDirectory`, the Agent service status and runtime summary are successful, Xray is running with at least one inbound, port forwarding is running with at least one service, pending events are empty, and host/guardrail evidence has no parse or enforcement errors. `ou-agent qf` wraps the host-side sequence into one command and saves the strict verifier transcript plus a machine-readable final summary with the Agent bundle directory and manifest/transcript path/size/SHA-256; `ou-agent qv --require-final-summary` revalidates the final-summary UTC `createdAt`, non-empty bundle directory against `manifest.bundleDirectory`, summary file paths, and transcript after archive transfer, while `ou-agent qvf` applies runtime and final-summary strict gates together.

The HTTP smoke target can use either the installed nginx secure-path URL or a direct backend URL and validates:

- public `/api/v1/boundary`
- anonymous rejection for protected `/api/v1/snapshot`
- `POST /api/v1/auth/session` login with returned HttpOnly cookie and CSRF token
- protected `/api/v1/snapshot`, `/api/v1/observability-metrics`, and `/metrics`
- sanitized runtime acceptance summary in `smoke-report.json`, optionally hardened by `--require-runtime-evidence`
- bounded `/events/v1/tasks?once=1` and `/events/v1/system-alerts?once=1` SSE responses
- optional missing-CSRF stateless POST probe expecting `403 csrf.required`
- `DELETE /api/v1/auth/session` logout

The script reads the installer credentials file at `/etc/ou-ui-next/credentials.env` by default, supports explicit `OU_UI_SMOKE_USERNAME` / `OU_UI_SMOKE_PASSWORD`, and does not print passwords, cookies, CSRF tokens, or backend bearer tokens. The installed CLI shortcut automatically injects the current panel URL and credentials-file path. `--report` / `OU_UI_SMOKE_REPORT_PATH` writes a sanitized JSON report with `0600` permissions for live acceptance archives. The default CSRF probe intentionally leaves sanitized `audit.denied` evidence and can be disabled with `OU_UI_SMOKE_CSRF_PROBE=0`, `sudo ou sm --skip-csrf-probe`, or `npm run smoke:production -- --skip-csrf-probe`.

- operator login through the browser form
- navigation to `主机探针`, `端口转发`, `订阅管理`, `安全策略`, `系统调优`, `执行记录`, and `审计日志`
- screenshot capture after each passed browser step when `--screenshot-dir` is set
- browser logout and return to the login page

The script reads the installer credentials file at `/etc/ou-ui-next/credentials.env` by default, supports explicit `OU_UI_BROWSER_SMOKE_USERNAME` / `OU_UI_BROWSER_SMOKE_PASSWORD`, and writes sanitized reports with `0600` permissions. It fails clearly when Playwright or browser binaries/system dependencies are unavailable; that failure is intentional acceptance evidence rather than a mocked pass.

The notification smoke target validates:

- operator login through the installed panel URL
- Telegram settings API reachability and whether the bot token is configured
- one explicit Telegram target, either an admin chat ID or a customer binding ID
- protected `POST /api/v1/integrations/telegram-bot/test` with CSRF and idempotency headers
- delivered test-notification status in the returned delivery record
- sanitized report output with only target kind and redacted delivery metadata

The script reads the installer credentials file at `/etc/ou-ui-next/credentials.env` by default, supports explicit `OU_UI_NOTIFICATION_SMOKE_USERNAME` / `OU_UI_NOTIFICATION_SMOKE_PASSWORD`, and writes sanitized reports with `0600` permissions. It fails when no target is provided, more than one target is provided, Telegram settings cannot be read, the test API is rejected, or the returned delivery is not `delivered`; those failures are preserved in `notification-smoke-report.json` when a report path is configured.

The webhook smoke target validates:

- webhook targets from explicit `--url` / `--urls` or installed `OU_UI_SYSTEM_ALERT_WEBHOOK_URL(S)`
- optional bearer token delivery without writing the token to reports
- default blocking for localhost, private, and link-local targets unless `--allow-local` is used for lab-only tests
- one sanitized JSON payload per target with request ID evidence
- passed HTTP status per target and sanitized target URL in `webhook-smoke-report.json`

The script writes reports with `0600` permissions and redacts URL path/query plus bearer tokens. In `ou qa`, webhook smoke is skipped by default and recorded as `webhook-smoke.txt` / `webhook-smoke-report.json`; `--include-webhook-smoke` performs the real delivery, and `ou qv --require-webhook-smoke` fails unless the archived report has `status=passed`, at least one passed target, and sanitized target URLs.

The archive smoke target validates:

- external archive sink configuration from the installed backend env or explicit `--env-file`
- local JSONL append paths for sanitized audit anchors, Agent log archive summaries, and traffic compaction buckets
- remote webhook/object-storage delivery callbacks and sanitized object-storage Object Lock summaries in the redacted report when those sinks are configured
- failure when no external archive sink is configured
- sanitized report output without webhook bearer tokens, object-storage access keys, secret keys, full URL paths, or query strings

The script writes reports with `0600` permissions. Because it performs real writes to local archive directories, external archive webhooks, and S3-compatible object storage, it is exposed as a standalone `ou as` / `npm run smoke:archive` command and is only included in `ou qa` when `--include-archive-smoke` is explicitly set. `ou qv --require-archive-smoke` fails unless the archived report has `status=passed`, all three archive checks passed, at least one configured sink is recorded, and remote target summaries are sanitized.
